`git checkout` is a Git command used primarily to:

- Switch from one branch to another.    
- Create and switch to a new branch.
- Check out a specific commit, resulting in a **detached HEAD** state.
- Restore files from a branch, commit, or the index.

> [!NOTE]  
> Modern Git also provides `git switch` for branch switching and `git restore` for restoring files. These commands separate responsibilities that were historically handled by `git checkout`.

---

## Basic Syntax

```bash
git checkout <branch>
```

Example:

```bash
git checkout main
```

This switches the working directory to the `main` branch and updates the working tree to match that branch.

The modern equivalent is:

```bash
git switch main
```

---

# Common `git checkout` Operations

|Operation|Command|
|---|---|
|Switch to a branch|`git checkout <branch>`|
|Create and switch to a branch|`git checkout -b <branch>`|
|Force-create/reset and switch|`git checkout -B <branch>`|
|Switch to previous branch|`git checkout -`|
|Check out a specific commit|`git checkout <commit>`|
|Create a branch from a commit|`git checkout -b <branch> <commit>`|
|Restore a file from the current index|`git checkout -- <file>`|
|Restore a file from another branch/commit|`git checkout <branch-or-commit> -- <file>`|
|Create an orphan branch|`git checkout --orphan <branch>`|

---

# Switch Between Branches

To switch to an existing branch:

```bash
git checkout main
```

For example:

```bash
git checkout feature/login
```

This changes `HEAD` to refer to the selected branch and updates the working tree to match it.

The modern command is:

```bash
git switch feature/login
```

> [!TIP]  
> For new Git workflows, prefer `git switch` when your intention is specifically to switch branches. `git checkout` remains useful because it supports several operations beyond branch switching.

---

# Create and Switch to a New Branch

Use the `-b` option:

```bash
git checkout -b <new-branch>
```

Example:

```bash
git checkout -b feature/login
```

This performs two operations:

1. Creates the new branch.
2. Switches `HEAD` to the new branch.

The modern equivalent is:

```bash
git switch -c feature/login
```

### Create a Branch from a Specific Commit

You can specify the starting point:

```bash
git checkout -b feature/login <commit>
```

For example:

```bash
git checkout -b feature/login abc1234
```

If no starting point is specified, the new branch starts from the current `HEAD`.

---

# `-B` — Create or Reset a Branch

The `-B` option is similar to `-b`, except that it resets the branch if it already exists.

```bash
git checkout -B <branch>
```

Conceptually:

```text
If branch does not exist:
    create it and switch to it

If branch already exists:
    reset it to the specified starting point and switch to it
```

> [!WARNING]  
> Because `-B` can move an existing branch reference, use it carefully.

---

# Tracking Remote Branches

When creating a local branch from a remote-tracking branch, Git can configure the local branch to track the remote branch.

For example:

```bash
git checkout -b feature/login origin/feature/login
```

You can explicitly request tracking with:

```bash
git checkout -b feature/login --track origin/feature/login
```

The modern equivalent is:

```bash
git switch --track origin/feature/login
```

When `--track` is used, Git configures an **upstream branch** for the new local branch.

This allows commands such as:

```bash
git pull
```

and:

```bash
git push
```

to know which remote branch the local branch is associated with.

---

# `--no-track`

To prevent Git from configuring an upstream branch:

```bash
git checkout --no-track -b feature/login origin/feature/login
```

This can be useful when you want a local branch based on a remote-tracking branch but do not want it to automatically track that remote branch.

---

# `--guess`

Git can automatically guess a remote-tracking branch when the requested local branch does not exist.

For example, if:

```text
origin/feature/login
```

exists but the local `feature/login` branch does not, Git may interpret:

```bash
git checkout feature/login
```

as equivalent to creating and tracking the remote branch:

```bash
git checkout -b feature/login --track origin/feature/login
```

`--guess` is the default behavior.

To disable it:

```bash
git checkout --no-guess feature/login
```

The behavior can also be controlled through:

```text
checkout.guess
```

---

# `checkout.defaultRemote`

If the same branch name exists on multiple remotes, Git may need help determining which remote should be used.

For example:

```text
origin/feature/login
upstream/feature/login
```

You can configure a preferred remote:

```bash
git config checkout.defaultRemote origin
```

This tells Git to prefer `origin` when resolving ambiguous remote branches.

---

# Switch to the Previously Checked-Out Branch

You can use:

```bash
git checkout -
```

The `-` is equivalent to:

```text
@{-1}
```

For example:

```bash
git checkout main
git checkout feature/login
git checkout -
```

The final command switches back to `main`.

You can also use:

```bash
git checkout @{-1}
```

# Detached HEAD

Normally, `HEAD` points to the current branch:

```text
HEAD
 |
 v
main
 |
 v
C
```

The branch points to a commit, so `HEAD` indirectly identifies the current commit.

When you check out a specific commit:

```bash
git checkout <commit>
```

`HEAD` points directly to that commit instead of pointing to a branch.

This is called **detached HEAD**.

Example:

```text
HEAD
 |
 v
B

A---B---C---D
        ^
        |
       main
```

Here:

- `main` points to commit `D`.
- `HEAD` points directly to commit `B`.
- You are not currently on a named branch.

---

# Why Use Detached HEAD?

Detached HEAD is useful when you want to:

- Inspect an older commit.
- Test the project at a particular point in history.
- Perform temporary experiments.
- Inspect a tagged release.

For example:

```bash
git checkout v2.0
```

or:

```bash
git checkout abc1234
```

If `v2.0` is a tag or `abc1234` is a commit, Git can place you in detached HEAD state.

> [!NOTE]  
> Detached HEAD is not inherently an error. It simply means that `HEAD` points directly to a commit rather than to a branch.

---

# Creating Commits in Detached HEAD

You can create commits while in detached HEAD state.

For example:

```text
A---B---C---D
    ^
    |
   HEAD
```

Create a new commit:

```text
A---B---E
    ^
    |
   HEAD

A---B---C---D
```

The new commit `E` is currently reachable through `HEAD`, but no branch points to it.

You can create additional commits:

```text
A---B---E---F
        ^
        |
       HEAD

A---B---C---D
```

If you then switch back to `main`:

```bash
git checkout main
```

`HEAD` points back to `main`:

```text
        E---F
       /
A---B---C---D
            ^
            |
           main
            ^
            |
           HEAD
```

Nothing may reference `F` anymore.

Git can eventually remove unreachable commits during garbage collection.

---

# Recovering Work from Detached HEAD

If you have created commits in detached HEAD and want to preserve them, create a branch before leaving the detached state:

```bash
git checkout -b my-experiment
```

Modern equivalent:

```bash
git switch -c my-experiment
```

The new branch points to the current commit:

```text
A---B---E---F
            ^
            |
       my-experiment
            ^
            |
           HEAD
```

You can also create a branch without switching:

```bash
git branch my-experiment
```

Or create a tag:

```bash
git tag my-experiment
```

---

# Recovering a Detached Commit with `git reflog`

If you have already switched away from the detached commit, you can often find it using the reflog:

```bash
git reflog -2 HEAD
```

or:

```bash
git log -g -2 HEAD
```

Once you identify the commit, create a branch pointing to it:

```bash
git branch recovered-work <commit>
```

---

# Restore a File from Another Branch or Commit

`git checkout` can also restore individual files.

For example:

```bash
git checkout main -- file.txt
```

This replaces `file.txt` in your working tree with the version from `main`.

Another example:

```bash
git checkout HEAD~2 -- Makefile
```

This restores `Makefile` from two commits before `HEAD`.

The modern command for restoring files is:

```bash
git restore --source=main -- file.txt
```

---

# The `--` Separator

Git can sometimes interpret an argument as either a branch/commit or a file.

The double dash:

```bash
--
```

tells Git that everything after it should be interpreted as paths rather than branch or commit names.

For example:

```bash
git checkout -- file.txt
```

This tells Git to treat `file.txt` as a file.

Similarly:

```bash
git checkout main -- file.txt
```

means:

> Take `file.txt` from `main` and restore it into the working tree.

> [!IMPORTANT]  
> The `--` separator is particularly useful when a branch and file have ambiguous or conflicting names.

---

# Restore Multiple Files

You can specify multiple files:

```bash
git checkout -- file1.txt file2.txt
```

You can also use a pattern:

```bash
git checkout -- '*.c'
```

The quotes prevent the shell from expanding the wildcard before Git receives it.

---

# Switching Branches with Local Changes

Git normally prevents you from switching branches if doing so would overwrite local modifications.

For example:

```bash
git checkout mytopic
```

may fail with a message similar to:

```text
error: Your local changes to 'frotz' would be overwritten by checkout.
```

This protects your uncommitted work.

You can either:

- Commit the changes.
- Stash the changes.
- Discard the changes if they are no longer needed.
- Use `git checkout -m` when appropriate.

---

# `-m` / `--merge`

The `--merge` option attempts to carry local modifications across the branch switch:

```bash
git checkout -m mytopic
```

If the local modifications do not conflict with the differences between the branches, Git can switch branches and reapply the changes.

Conceptually:

```text
Current branch
     |
     | local changes
     v
git checkout -m target
     |
     v
Target branch + local changes
```

If the local changes conflict with the target branch, conflicts can occur.

> [!WARNING]  
> `git checkout -m` does not mean "ignore conflicts." Local changes may still result in conflicts when reapplied.

---

# Detached HEAD vs. Branch Checkout

|Command|Result|
|---|---|
|`git checkout main`|Switches to `main`|
|`git checkout feature/login`|Switches to `feature/login`|
|`git checkout -b feature/login`|Creates and switches to a new branch|
|`git checkout abc1234`|Checks out a commit; detached HEAD|
|`git checkout v2.0`|Checks out the tag; typically detached HEAD|
|`git checkout -`|Switches to the previously checked-out branch|
|`git checkout main -- file.txt`|Restores `file.txt` from `main`|

---

# `--orphan` — Create an Unrelated History

The `--orphan` option creates a new branch whose first commit has **no parent**.

```bash
git checkout --orphan new-branch
```

The new branch starts from the specified starting tree, but its first commit creates a completely separate history.

This can be useful when you need a branch containing files without the existing repository's commit history.

For example:

```text
Existing history:

A---B---C---D
            ^
           main

New orphan history:

X
^
new-branch
```

The first commit `X` has no parent.

> [!NOTE]  
> An orphan branch is different from a detached HEAD. An orphan branch is a real branch; it simply starts a new, disconnected history.

---

# Sparse Checkout

The `--ignore-skip-worktree-bits` option is relevant when using sparse checkout.

```bash
git checkout --ignore-skip-worktree-bits -- <paths>
```

It allows the specified paths to be checked out even when sparse-checkout patterns would normally exclude them.

---

# Submodules

The `--recurse-submodules` option updates active submodules to the commits recorded by the superproject:

```bash
git checkout --recurse-submodules <branch>
```

Without this option, submodule working trees are generally not updated as part of the checkout.

You can explicitly disable recursive submodule checkout with:

```bash
git checkout --no-recurse-submodules <branch>
```

---

# Overlay Mode

Git checkout normally operates in **overlay mode**.

```bash
git checkout --overlay <branch>
```

In overlay mode, files that exist in the current working tree but not in the target tree are not automatically removed.

With:

```bash
git checkout --no-overlay <branch>
```

Git can remove files that are present in the current tree but absent from the target tree, making the affected paths match the target more exactly.

---

# Parallel Checkout

Git can use multiple workers when updating the working tree.

Configure the number of workers with:

```bash
git config checkout.workers <number>
```

For example:

```bash
git config checkout.workers 4
```

You can also configure the minimum number of files required before parallel checkout is attempted:

```bash
git config checkout.thresholdForParallelism <number>
```

The default threshold is 100 files.

> [!NOTE]  
> Parallel checkout can improve performance for some repositories and storage configurations, but sequential checkout can be faster in other environments.

|---|---|
|`-b`|Create and switch to a new branch|

|`--no-overlay`|Remove files absent from the target tree|
|`--`|Separate options from file paths|

# `git checkout` vs. `git switch` vs. `git restore`

Modern Git provides more focused commands:

|Task|Older command|Modern command|
|---|---|---|
|Switch branches|`git checkout main`|`git switch main`|
|Create + switch branch|`git checkout -b feature`|`git switch -c feature`|
|Restore a file|`git checkout -- file.txt`|`git restore file.txt`|
|Restore from another branch|`git checkout main -- file.txt`|`git restore --source=main -- file.txt`|
|Detached HEAD|`git checkout <commit>`|`git switch --detach <commit>`|

> [!TIP]  
> `git checkout` is still a valid and widely used Git command. `git switch` and `git restore` were introduced to make the two major use cases—branch switching and file restoration—more explicit.

# Key Concepts

### `HEAD`

`HEAD` identifies your current position in the repository.

Normally:

```text
HEAD
 |
 v
main
 |
 v
commit
```

In detached HEAD state:

```text
HEAD
 |
 v
commit
```

### Branch

A branch is a movable reference pointing to a commit.

### Detached HEAD

A state where `HEAD` points directly to a commit rather than to a branch.

### Working Tree

The files currently checked out on disk.

### Index / Staging Area

The staging area contains the changes that are prepared for the next commit.

# Typical Branch-Switching Workflow

```bash
# Check current branch and working-tree state
git status

# List branches
git branch

# Switch to main
git checkout main

# Or use the modern command
git switch main

# Create and switch to a feature branch
git checkout -b feature/login

# Or
git switch -c feature/login
```

# Key Takeaways

- `git checkout` can switch branches, restore files, create branches, and check out commits.
- `git checkout <branch>` switches to an existing branch.
- `git checkout -b <branch>` creates and switches to a new branch.
- `git checkout <commit>` places `HEAD` in a detached state.
- Detached HEAD is useful for inspecting commits and performing temporary experiments.
- Create a branch or tag if you want to preserve commits created while in detached HEAD.
- `git checkout -- <file>` restores a file from the index.
- `git checkout <branch> -- <file>` restores a file from another branch.
- `--` helps Git distinguish file paths from branch or commit names.
- `git checkout -m` attempts to carry local modifications across a branch switch.
- `git switch` is the modern command for branch switching.
- `git restore` is the modern command for restoring files.
