# What Is a Merge?

A **merge** in Git is the process of combining changes from one branch into another branch.

For example, if you have:

```text
main
feature/login
```

and want to integrate the changes from `feature/login` into `main`, you switch to the target branch and run:

```bash
git merge feature/login
```

The branch you are currently on is the **target branch**, and the branch specified in `git merge` is the **source branch**.

> [!IMPORTANT]  
> A merge does not always create a new merge commit. If Git can perform a **fast-forward merge**, it simply moves the target branch pointer forward. A new merge commit is created when the histories have diverged and a three-way merge is required.

---

# Basic Branching Workflow

A common real-world workflow might look like this:

1. Work on the main project.
2. Create a branch for a new feature or user story.
3. Work on the feature branch.
4. An urgent production issue appears.
5. Switch back to the production branch.
6. Create a branch for the hotfix.
7. Implement and test the hotfix.
8. Merge the hotfix into the production branch.
9. Delete the hotfix branch.
10. Switch back to the original feature branch.
11. Continue working on the feature.
12. Eventually merge the feature branch into the main branch.

# Creating a Feature Branch

Suppose the repository currently has a `master` branch with several commits:

```text
A---B---C
        ^
        |
      master
```

You want to work on issue `#53`.

You can create a new branch and switch to it at the same time:

```bash
git checkout -b iss53
```

This is equivalent to:

```bash
git branch iss53
git checkout iss53
```

The resulting history looks like:

```text
A---B---C
        ^
        |
      iss53
        ^
        |
       HEAD

      master
        |
        v
        C
```

The important point is that `iss53` initially points to the same commit as `master`.

# Working on the Feature Branch

Once `iss53` is checked out, you can make changes and commit them:

```bash
vim index.html
git commit -a -m "Create new footer [issue 53]"
```

The `iss53` branch moves forward when you create a new commit:

```text
A---B---C---D
        ^   ^
      master iss53
            ^
           HEAD
```

Because `iss53` is the current branch, `HEAD` points to `iss53`, which points to the newest commit.

---

# Switching to Another Branch

Suppose an urgent production issue appears while you are working on `iss53`.

If your changes are committed, you can switch back to `master`:

```bash
git checkout master
```

Modern Git equivalent:

```bash
git switch master
```

Git updates the working directory so that it matches the state represented by the `master` branch.

> [!IMPORTANT]  
> When switching branches, Git updates files in the working tree by adding, removing, or modifying them so that they match the target branch's current commit.

If you have uncommitted changes that would be overwritten by the branch switch, Git normally prevents the switch.

Here:

- `master` points to `C`.
- `iss53` contains the feature work.
- `hotfix` contains the production fix.

# Fast-Forward Merge

After testing the hotfix, switch back to `master`:

```bash
git checkout master
```

Then merge the hotfix:

```bash
git merge hotfix
```

Git may output something similar to:

```text
Updating f42c576..3a0874c
Fast-forward
 index.html | 2 ++
 1 file changed, 2 insertions(+)
```

## What Is a Fast-Forward Merge?

A **fast-forward merge** occurs when the target branch is an ancestor of the source branch.

Before the merge:

```text
A---B---C---D
        ^   ^
      master hotfix
```

Since `master` points to `C` and `D` is directly ahead of `C`, Git does not need to create another commit.

It simply moves the `master` pointer forward:

```text
A---B---C---D
            ^
         master
         hotfix
```

No merge commit is created.

```bash

```

Then:


# Basic Merging

Suppose the work on `iss53` is now complete.

Switch to the branch that should receive the changes:

```bash
git checkout master
```

Then merge `iss53`:

```bash
git merge iss53
```

When the histories have diverged, Git performs a **three-way merge**.

---

# Three-Way Merge

Consider this history:

```text
          D---E  iss53
         /
A---B---C
        ^
        |
      master
```

The branches have diverged from commit `C`.

Git uses three snapshots:

1. The common ancestor — `C`.
2. The current branch tip — `master`.
3. The branch being merged — `iss53`.

Conceptually:

```text
             C
            / \
           /   \
      master   iss53
        |        |
        v        v
        X        E
```

Git compares the changes made on both sides since their common ancestor and combines them.

# Merge Commit

Because the histories have diverged, Git creates a new **merge commit**:

```text
          D---E
         /     \
A---B---C-------M
                ^
              master
```

The merge commit `M` has **two parents**:

- The previous `master` commit.
- The tip of `iss53`.

Example:

```bash
git checkout master
git merge iss53
```

Git may report:

```text
Merge made by the 'ort' strategy.
index.html | 1 +
1 file changed, 1 insertion(+)
```

> [!NOTE]  
> Modern Git commonly uses the `ort` merge strategy for ordinary two-branch merges. Older Git documentation and examples may show the `recursive` strategy.

---

# Fast-Forward vs. Three-Way Merge

|Feature|Fast-forward|Three-way merge|
|---|---|---|
|Branch histories diverged?|No|Yes|
|New merge commit?|No|Yes|
|Target branch pointer moves forward?|Yes|Yes, to the new merge commit|
|Common ancestor used for comparison?|Not required for the merge itself|Yes|
|Example|`master` is behind `hotfix`|`master` and `iss53` both have unique commits|

### Fast-forward

```text
Before:

A---B---C
        ^
      master
        \
         D
         ^
       hotfix

After:

A---B---C---D
            ^
        master
        hotfix
```

### Three-way merge

```text
Before:

      D---E
     /     ^
    /    iss53
A---B---C
        ^
      master

After:

      D---E
     /     \
A---B---C---M
            ^
          master
```

# Merge Conflicts

Sometimes Git cannot automatically combine the changes.

A conflict can occur when both branches modify the same part of the same file in incompatible ways.

For example:

```bash
git merge iss53
```

Git may report:

```text
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.
```

At this point, Git **does not create the merge commit yet**.

The merge is paused until the conflicts are resolved.

---

# Check for Merge Conflicts

Run:

```bash
git status
```

You may see:

```text
On branch master
You have unmerged paths.
  (fix conflicts and run "git commit")

Unmerged paths:
  (use "git add <file>..." to mark resolution)

    both modified:   index.html
```

Files listed as **unmerged** still require conflict resolution.

---

# Conflict Markers

Git inserts conflict markers into files that contain conflicts.

For example:

```html
<<<<<<< HEAD:index.html
<div id="footer">contact : email.support@github.com</div>
=======
<div id="footer">
    please contact us at support@github.com
</div>
>>>>>>> iss53:index.html
```

The markers identify the competing versions.

### `<<<<<<< HEAD`

Everything between:

```text
<<<<<<< HEAD
```

and:

```text
=======
```

represents the version from the branch currently checked out.

In this example, that is `master`.

### `=======`

This separates the two versions.

### `>>>>>>> iss53`

Everything between:

```text
=======
```

and:

```text
>>>>>>> iss53
```

represents the version from the branch being merged.

> [!IMPORTANT]  
> The conflict marker labels depend on the merge context. `HEAD` refers to the current branch, while the final marker identifies the other side of the conflict.

---

# Resolving a Merge Conflict Manually

You must edit the conflicted file and decide what the final version should contain.

For example, you could replace the conflict with:

```html
<div id="footer">
    please contact us at email.support@github.com
</div>
```

Make sure all conflict markers are removed:

```text
<<<<<<<
=======
>>>>>>>
```

Then save the file.

---

# Mark the Conflict as Resolved

After resolving the file, stage it:

```bash
git add index.html
```

Staging the file tells Git that you have resolved the conflict.

Check the status:

```bash
git status
```

You may see:

```text
On branch master
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:

    modified:   index.html
```

---

# Complete the Merge

Once all conflicts have been resolved and staged:

```bash
git commit
```

Git will normally provide a default merge commit message such as:

```text
Merge branch 'iss53'
```

You can modify the message if additional context about the conflict resolution would be useful.

# Complete Merge-Conflict Workflow

A typical conflict-resolution workflow is:

```bash
# Switch to the target branch
git checkout master

# Merge the source branch
git merge iss53

# If conflicts occur, inspect the status
git status

# Edit conflicted files and resolve the conflicts

# Stage resolved files
git add index.html

# Verify
git status

# Complete the merge
git commit
```

---

# Aborting a Merge

If you are in the middle of a merge and decide that you do not want to continue, you can usually abort the merge with:

```bash
git merge --abort
```

This attempts to return the repository to the state it was in before the merge began.

> [!TIP]  
> Before resolving a complicated merge, make sure you understand whether you want to continue the merge or abort it. `git merge --abort` is particularly useful when you realize that you started the merge from an unsuitable working state.

# Branching and Merging Example

The complete feature/hotfix workflow can be summarized as:

```bash
# Create feature branch
git checkout -b iss53

# Work and commit
git commit -a -m "Create new footer [issue 53]"

# Switch to production branch
git checkout master

# Create hotfix branch
git checkout -b hotfix

# Fix and commit
git commit -a -m "Fix broken email address"

# Merge hotfix into master
git checkout master
git merge hotfix

# Delete completed hotfix branch
git branch -d hotfix

# Return to feature work
git checkout iss53

# Continue working
git commit -a -m "Finish the new footer [issue 53]"

# Eventually merge the feature
git checkout master
git merge iss53

# Delete completed feature branch
git branch -d iss53
```

# Important Concepts

## Source Branch vs. Target Branch

If you run:

```bash
git checkout master
git merge iss53
```

then:

- `master` = **target branch**
- `iss53` = **source branch**

The changes from `iss53` are integrated into `master`.

> [!IMPORTANT]  
> The branch you are currently on is the branch that receives the merge.

---

## Merge Does Not Copy a Branch

A merge does not copy one branch into another.

Instead, Git combines the histories represented by the branches and updates the target branch with the resulting history.

---

## A Branch Is Not a Container

A branch is a movable reference to a commit.

For example:

```text
      D---E  feature
     /
A---B---C
        ^
        |
       main
```

Merging `feature` into `main` changes the history reachable from `main`; it does not physically move the commits from one "container" to another.

---

# Key Takeaways

- `git merge` combines changes from one branch into another.
- The branch currently checked out is the **target** of the merge.
- The branch specified in `git merge <branch>` is the **source**.
- A **fast-forward merge** occurs when the target branch is an ancestor of the source branch.
- Fast-forward merges do not create a merge commit.
- A **three-way merge** is used when branch histories have diverged.
- A three-way merge normally creates a **merge commit** with two parents.
- Git may encounter conflicts when both branches modify the same parts of files incompatibly.
- Conflict resolution involves:
    1. Identifying conflicted files.
    2. Editing the files.
    3. Removing conflict markers.
    4. Running `git add` on resolved files.
    5. Running `git commit` to complete the merge.
- `git mergetool` can provide a graphical interface for resolving conflicts.
- `git merge --abort` can be used to abandon an in-progress merge.
- After a branch has been successfully merged and is no longer needed, it can usually be deleted with `git branch -d <branch>`.
