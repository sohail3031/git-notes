# Committing Changes

Committing saves a snapshot of the **staged changes** to the repository's history, along with a message describing what was changed and why.

Each commit has a unique **SHA hash** that identifies it and allows Git to track the exact state of the project at that point in time. Commits build the timeline of a repository that developers can browse, compare, and revert to later.

---

## Git Commit

The `git commit` command creates a commit, which represents a snapshot of the repository.

```bash
git commit -m "update the README.md with link to contributing guide"
```

Commits should generally be made frequently and should represent **logical units of change**. Over time, a well-structured commit history should tell the story of how the repository evolved.

A commit contains more than just the changes themselves. It also includes metadata such as:

- Author
- Committer
- Timestamp
- Commit message
- Parent commit(s)
- Commit SHA

### Important Concept

A commit records the state represented by the **staging area** at the time the commit is created.

Git does **not** automatically commit every modified file in your working directory.

---

## How Git Commit Works

Commits are the building blocks of **save points** within Git's version control system.

A typical workflow is:

```text
Working Directory
       ↓
   git add
       ↓
Staging Area
       ↓
  git commit
       ↓
Repository History
```

Before committing, it is a good practice to check your current state:

```bash
git status
```

This allows you to verify:

- Which branch you are currently on
- Which files have been modified
- Which changes are staged
- Which changes are unstaged

---

## Commits Shape History

Commits allow you to intentionally and safely build your project's history.

You can:

- Create commits on different branches.
- Choose exactly which changes belong in a commit.
- Compare changes between commits.
- Revert previous changes.
- Browse the evolution of a project.

Commits are created on the branch that is currently checked out, meaning the branch where `HEAD` is pointing.

Therefore, it is a good practice to run:

```bash
git status
```

before committing to confirm that you are on the intended branch.

Before committing new changes, stage them using:

```bash
git add <file>
```

### Git Commit Objects

Commits are Git objects identified by SHA hashes. Git is designed to handle repositories containing many files and many commits efficiently.

---

# Committing in Two Phases

Git separates the process of creating a commit into two main phases:

1. **Stage the changes**
2. **Commit the staged changes**

This separation allows you to create **logical and atomic commits**.

For example, suppose you modify three files:

```text
README.md
login.py
database.py
```

You may decide that only the changes to `README.md` and `login.py` belong in the current commit.

You can stage only those files:

```bash
git add README.md login.py
```

Then commit them:

```bash
git commit -m "update login documentation and validation"
```

The changes in `database.py` remain unstaged and are not included in the commit.

---

## Stage Specific Parts of a File

You can use:

```bash
git add -p
```

The `-p` option allows you to interactively review individual changes (hunks) and choose which changes to stage.

This is particularly useful when a single file contains changes belonging to multiple logical tasks.

# Common `git commit` Commands

## `git commit`

```bash
git commit
```

Starts the commit process and opens your configured text editor so you can enter the commit message.

If no editor has been configured, Git may use an editor such as **Vim**.

For Vim, you can save and exit with:

```text
Esc
:wq
Enter
```

---

## `git commit -m`

```bash
git commit -m "descriptive commit message"
```

Creates a commit and specifies the commit message directly.

Example:

```bash
git commit -m "update README with contributing guide"
```

This is one of the most commonly used forms of `git commit`.

---

## `git commit -am`

```bash
git commit -am "descriptive commit message"
```

The `-a` option automatically stages changes to **already tracked files** and then creates the commit.

For example:

```bash
git commit -am "update login validation"
```

### Important

`git commit -am` does **not** automatically stage new, untracked files.

For example, if you create:

```text
new-feature.py
```

you still need:

```bash
git add new-feature.py
git commit -m "add new feature"
```

---

## `git commit --amend`

```bash
git commit --amend
```

Replaces the most recent commit with a new commit.

It is useful when:

- The commit message contains a spelling mistake.
- You forgot to include a change.
- You want to modify the most recent commit.
- The commit has not been pushed to a shared remote repository.

More details are covered in [Updating Commits With Git Commit Amend](https://chatgpt.com/c/6aac412f-bc10-83ea-958b-2516684c09f9#updating-commits-with-git-commit-amend).

# Changing or Undoing Commits

Sometimes you may need to modify or undo a commit.

Before changing commit history, consider whether the commit has already been shared with other developers.

### Local vs. Shared History

- Changing commits that exist **only locally** is generally safer.
- Changing commits that have already been pushed to a **shared remote repository** can cause problems for collaborators.
- Rewriting shared history may require a force push and can cause other developers to deal with conflicting histories.

> [!WARNING]  
> Be especially careful when rewriting history that has already been pushed to a shared repository.

---

# What Can Go Wrong When Changing History?

Consider this situation:

1. You and another developer have the same repository history.
2. The other developer removes the most recent commit from their branch history. 
3. They continue making new commits from an earlier commit.
4. Meanwhile, you continue working from the original history that still contains the removed commit.
5. The other developer pushes their rewritten history.
6. You later push your work based on the old history.

The two repositories now have different histories.

Git may require you to reconcile the histories before the changes can be pushed.

More importantly, a commit that someone intended to remove may be reintroduced into the shared history.

For example, if the removed commit contained:

- A password
- An API token
- A secret key
- A large binary file

the sensitive data may return to the repository history.

> [!WARNING]  
> Removing sensitive information from Git history can require more than simply deleting the file from the latest commit. Secrets may continue to exist in previous commits and may need to be rotated or removed from the repository history.

---

# `git revert`

The `git revert` command is generally the safest way to undo a commit that has already been shared.

```bash
git revert <commit-hash>
```

Instead of deleting the existing commit, `git revert`:

1. Examines the changes introduced by the specified commit.
2. Creates the inverse of those changes.
3. Creates a **new commit** containing those inverse changes.

Conceptually:

```text
Commit A
   ↓
Commit B
   ↓
Commit C
```

If you revert `Commit C`:

```text
Commit A
   ↓
Commit B
   ↓
Commit C
   ↓
Revert Commit C
```

The original commit remains part of the history.

This preserves the integrity and traceability of the repository's history.

# `git reset`

The `git reset` command can move the `HEAD` and current branch pointer to another commit.

```bash
git reset <commit>
```

Depending on the reset mode, it can also modify the staging area and working directory.

Reset modes include:

```bash
git reset --soft
git reset --mixed
git reset --hard
```

### Before Using `git reset`

- Determine whether the commits are already shared with other developers.
- Understand the differences between `--soft`, `--mixed`, and `--hard`.
- Make sure you do not have uncommitted work that you may lose.
- Be especially careful with `--hard`.

> [!WARNING]  
> `git reset --hard` can discard uncommitted changes in the working directory and staging area. Use it only when you understand exactly what will be removed.

---

# `git reflog`

When working with rewritten history, `git reflog` can help you recover references to previous states of `HEAD`.

```bash
git reflog
```

The reflog records updates to references such as `HEAD`.

For example, if you accidentally run a reset and appear to lose a commit, the reflog may contain the previous commit reference.

Example:

```text
HEAD@{0}: reset: moving to HEAD~1
HEAD@{1}: commit: add login validation
```

You can use the commit hash shown in the reflog to locate the previous state.

> [!NOTE]  
> The reflog is primarily a local recovery mechanism. It is not the same thing as the shared repository history.

---

# Updating Commits With `git commit --amend`

```bash
git commit --amend
```

`git commit --amend` changes the most recent commit on the current branch.

It is especially useful when the latest commit:

- Has a spelling mistake in the commit message.
- Is missing changes that should have been included.
- Needs a small correction before being shared.

### Example

Suppose you created:

```bash
git commit -m "add user authentcation"
```

The commit message contains a spelling mistake.

You can correct it with:

```bash
git commit --amend -m "add user authentication"
```

You can also stage an additional change and then amend the previous commit:

```bash
git add login.py
git commit --amend
```

> [!WARNING]  
> `git commit --amend` rewrites the most recent commit. It is safest to use it before the commit has been pushed to a shared remote repository.

# Writing Good Commit Messages

Once you have staged the files you want to include, you are ready to commit.

A good commit message should be:

- Short
- Clear
- Descriptive
- Focused on the change
- Written consistently across the project

Good commit messages make it easier to understand the history of a repository.

## Commit Message Examples

```bash
git commit -m "create file structure for Git guides"
```

```bash
git commit -m "translate Git cheat sheet into German"
```

```bash
git commit -m "update broken URL to Git resources"
```

### Use the Imperative Mood

Commit messages are commonly written in the **imperative mood**, as if giving an instruction.

Examples:

```text
create file structure
update documentation
fix login validation
add API tests
remove deprecated configuration
```

Avoid unnecessarily vague messages such as:

```text
changes
updates
fixes
work
stuff
```

---

# Extended Commit Messages

If a change requires more context, Git allows you to create a commit message with both a short summary and a longer description.

For example:

```text
Add login validation

Validate required login fields before submitting
the authentication request. Add test coverage for
empty username and password values.
```

This can be useful for explaining **why** a change was made, especially for larger or more complex changes.

# Related Commands

|Command|Purpose|
|---|---|
|`git add <file>`|Stages a file for the next commit|
|`git add -p`|Interactively stages individual changes|

|`git commit`|Creates a commit from staged changes|
|`git commit -m "message"`|Creates a commit with a message|
|`git commit -am "message"`|Stages modifications to tracked files and commits them|
|`git commit --amend`|Replaces the most recent commit|
|`git revert <commit>`|Creates a new commit that reverses an earlier commit|

|`git push`|Uploads local commits to a remote repository|
|`git log`|Displays and explores commit history|

# Typical Commit Workflow

A common Git workflow looks like this:

```bash
# 1. Check the current state
git status

# 2. Stage the desired changes
git add <file>

# 3. Check what is staged
git status

# 4. Create the commit
git commit -m "add login validation"

# 5. Review the commit history
git log

# 6. Push the commit to the remote repository
git push
```

```text

│                     │
│  Modified files     │

           │
        git push
           │
           ▼
┌─────────────────────┐
│   Remote Repository │
└─────────────────────┘
```

# Key Takeaways

- `git commit` records the **staged changes** as a new commit.
- A commit represents a snapshot of the repository at a specific point in time.
- Each commit has a unique SHA identifier.
- Commits should represent logical units of change.
- `git status` should be used before committing to verify the current branch and staged changes.
- `git add` selects changes for the next commit.
- `git add -p` allows you to stage individual parts of a file.
- `git commit -m "message"` creates a commit with an inline message.
- `git commit -am "message"` automatically stages modifications to tracked files but does not stage new files.
- `git commit --amend` modifies the most recent commit.
- `git revert` creates a new commit that reverses an earlier commit and is generally appropriate for undoing changes in shared history.
- `git reset` moves `HEAD` and the current branch pointer and must be used carefully.
- `git reflog` can help recover previous local states of `HEAD`.
- Avoid rewriting history that has already been shared unless you understand the consequences.
- Good commit messages make project history easier to understand and maintain.
