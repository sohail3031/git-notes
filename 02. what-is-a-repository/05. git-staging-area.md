# Git Staging Area

The **staging area**, also called the **index**, is where changes are prepared before they are committed.

The staging area allows you to choose exactly which changes should be included in the next commit.

The basic workflow is:

```text
Working Directory
       │
       │ git add
       ▼
Staging Area
       │
       │ git commit
       ▼
Git Repository
```

> [!important]  
> The staging area acts as an intermediate step between your working directory and a commit. It allows you to select which changes should be included in the next version of your project.

---

# What Are Staged Changes?

**Staged changes** are changes that have been added to the staging area using `git add`.

For example, suppose your project contains:

```text
my-project/
├── src/
│   ├── file1.js
│   └── file2.js
└── README.md
```

You make changes to all three files:

- Add a comment to `file1.js`
- Add a constant variable to `file2.js`
- Add some text to `README.md`

At this point, all three files have changes in the **working directory**, but none of them have been staged.

Run:

```bash
git status
```

Git may show:

```text
Changes not staged for commit:
    modified:   src/file1.js
    modified:   src/file2.js
    modified:   README.md
```

These are **unstaged changes**.

---

# Staging Changes with `git add`

To move a specific file's changes into the staging area, use:

```bash
git add <file>
```

For example:

```bash
git add src/file1.js
```

Now check the repository status:

```bash
git status
```

You may see:

```text
Changes to be committed:
    modified:   src/file1.js

Changes not staged for commit:
    modified:   src/file2.js
    modified:   README.md
```

`src/file1.js` is now a **staged change**.

The other two files are still **unstaged changes**.

---

# Staging Multiple Files

You can stage multiple files with a single command:

```bash
git add src/file1.js src/file2.js
```

Now:

```bash
git status
```

may show:

```text
Changes to be committed:
    modified:   src/file1.js
    modified:   src/file2.js

Changes not staged for commit:
    modified:   README.md
```

The staging area now contains the changes to `file1.js` and `file2.js`, while the changes to `README.md` remain outside the staging area.

---

# Creating a Commit from the Staging Area

Once you have selected the changes you want to include, create a commit:

```bash
git commit -m "Add new changes"
```

The commit records a **snapshot of the changes currently in the staging area**.

In this example, the commit includes:

```text
src/file1.js
src/file2.js
```

But it does **not** include:

```text
README.md
```

because `README.md` was not staged.

---

# What Happens to the Staging Area After a Commit?

After the commit is created, the staged changes have been recorded in Git's history.

Run:

```bash
git status
```

You may now see:

```text
Changes not staged for commit:
    modified:   README.md
```

The changes to `file1.js` and `file2.js` are no longer shown as staged because they were included in the commit.

The `README.md` change remains because it was never added to the staging area.

---

# Why Does Git Have a Staging Area?

The staging area gives you control over what goes into each commit.

Suppose you modified five files:

```text
file1.js
file2.js
file3.js
README.md
config.js
```

You may not want all five changes in the same commit.

For example, you could stage only:

```bash
git add file1.js file2.js
```

and commit them:

```bash
git commit -m "Update application logic"
```

Then stage the documentation separately:

```bash
git add README.md
git commit -m "Update documentation"
```

This produces smaller, more focused commits.

> [!tip]  
> A good commit generally represents one logical change. The staging area makes it possible to select exactly which changes belong to that commit.

# `git status`

The `git status` command shows the current state of your Git repository.

```bash
git status
```

It helps you identify:

- Changes that have been staged
- Changes that have not been staged
- Untracked files
- The current branch
- Other repository status information

For example:

```text
Changes to be committed:
    modified:   src/file1.js

Changes not staged for commit:
    modified:   README.md
```

You can interpret this as:

```text
src/file1.js
    ↓
Staged
    ↓
Will be included in the next commit


README.md
    ↓
Unstaged
    ↓
Will NOT be included in the next commit
```

# Two Phases of Creating a Commit

A simplified Git commit workflow can be viewed as two main phases.

## Phase 1: Stage the Changes

Use:

```bash
git add <file>
```

This moves the selected changes from the working directory into the staging area.

```text
Working Directory
       │
       │ git add
       ▼
Staging Area
```

## Phase 2: Commit the Staged Changes

Use:

```bash
git commit -m "Commit message"
```

This creates a commit containing the changes currently staged.

```text
Staging Area
       │
       │ git commit
       ▼
Git Repository
```

---

# Staging Area as a Snapshot

A useful way to think about the staging area is as a **draft of your next commit**.

```text
Working Directory
      │
      │ Select changes
      │
      ▼
Staging Area
      │
      │ Take snapshot
      │
      ▼
    Commit
```

When you run:

```bash
git commit -m "My changes"
```

Git creates a snapshot based on what is currently staged.

> [!important]  
> `git commit` does not automatically commit every modified file in your working directory. It commits the changes that have been staged.

# Example Workflow

Suppose you modify three files:

```text
src/file1.js
src/file2.js
README.md
```

### Step 1: Check the Status

```bash
git status
```

Result:

```text
Changes not staged for commit:
    modified:   src/file1.js
    modified:   src/file2.js
    modified:   README.md
```

### Step 2: Stage Two Files

```bash
git add src/file1.js src/file2.js
```

### Step 3: Check the Status Again

```bash
git status
```

Result:

```text
Changes to be committed:
    modified:   src/file1.js
    modified:   src/file2.js

Changes not staged for commit:
    modified:   README.md
```

### Step 4: Create the Commit

```bash
git commit -m "Update source files"
```

### Step 5: Check the Status

```bash
git status
```

The `README.md` modification remains unstaged because it was not included in the commit.

---

# Inspecting the Commit

After creating a commit, you can view the commit history with:

```bash
git log
```

For a shorter format:

```bash
git log --oneline
```

The newly created commit will appear in the history.

The commit contains the staged changes that were present when `git commit` was executed.

# Working Directory → Staging Area → Repository

The complete flow can be visualized as:

```text
┌──────────────────────┐
│   Working Directory  │
│                      │
│  Modified files      │
│  New files           │
│  Untracked files     │
└──────────┬───────────┘
           │
           │ git add
           ▼
┌──────────────────────┐
│    Staging Area      │
│       (Index)        │
│                      │
│ Selected changes     │
│ for next commit      │
└──────────┬───────────┘
           │
           │ git commit
           ▼
┌──────────────────────┐
│   Git Repository     │
│                      │
│   Commit / Snapshot  │
└──────────────────────┘
```

# Key Terms

|Term|Meaning|
|---|---|
|**Working Directory**|The files you currently work on and modify|
|**Staging Area**|The changes selected for the next commit|
|**Index**|Another name for the staging area|
|**Staged Change**|A change that has been added to the staging area|
|**Unstaged Change**|A modification in the working directory that has not been staged|
|**Commit**|A recorded snapshot of the staged changes|
|`git add`|Moves selected changes into the staging area|
|`git commit`|Records the staged changes as a commit|
|`git status`|Shows the current state of the repository|
|`git log`|Displays commit history|

> [!summary]  
> **Remember the three main areas:**
> 
> **Working Directory** → where you make changes  
> **Staging Area** → where you select changes for the next commit  
> **Git Repository** → where committed snapshots are stored
> 
> The basic workflow is:
> 
> ```bash
> git add <file>
> git commit -m "Commit message"
> ```
